Chapter 1 · Beginner

Day 1. You have data. Now what?

You've just opened Python for the first time. You've heard of Pandas. You've heard it can do "data stuff". But what does that actually mean?

Here's the truth: Pandas is just a really powerful way to work with tables in Python. Think of it as Excel — but programmable, reproducible, and capable of handling millions of rows without breaking a sweat.

Let's start from the very beginning. No assumptions. Just curiosity.

1
What even is a DataFrame?
Beginner
Before you write any code, you need the right mental model. A DataFrame is just a table. Rows and columns. Like a spreadsheet. That's it. And a Series is just one column of that table — a list with a label on each item.

Think of it this way: if your data lives in Excel, a DataFrame is the sheet, and a Series is one of the columns you'd click on.
Analogy

A DataFrame = an entire spreadsheet (rows + columns)
A Series = one single column of that spreadsheet
An index = the row numbers on the left side (like line numbers in Excel)

import pandas as pd

# A Series — just a labelled list
s = pd.Series([85, 92, 78, 95], index=['Alice', 'Bob', 'Charlie', 'Diana'])
print(s['Bob'])
# 92

# A DataFrame — a full table
df = pd.DataFrame({
    'Name':  ['Alice', 'Bob', 'Charlie'],
    'Score': [85, 92, 78],
    'City':  ['London', 'Paris', 'London']
})
print(df)
#       Name  Score    City
# 0    Alice     85  London
# 1      Bob     92   Paris
# 2  Charlie     78  London
✅ The numbers 0, 1, 2 on the left are the index — Pandas adds these automatically. You can replace them with meaningful labels later (like dates or names).
2
Loading real data — your first CSV
Beginner
You're not going to be typing data by hand. Real data lives in files — CSV, Excel, databases. The most common is CSV (Comma Separated Values). Loading it into Pandas takes one line. 
# Load a CSV file
df = pd.read_csv('sales_data.csv')

# Load an Excel file
df = pd.read_excel('report.xlsx', sheet_name='Q1')

# Load a JSON file
df = pd.read_json('data.json')

# Load straight from the internet (yes, really)
url = 'https://raw.githubusercontent.com/datasciencedojo/datasets/master/titanic.csv'
df = pd.read_csv(url)

# Save your work back to CSV
df.to_csv('cleaned_data.csv', index=False)
💡 index=False when saving means "don't write the row numbers into the file." Without it, you'd get an ugly extra column called "Unnamed: 0" every time you reload the file.
3
Exploring your dataset — the first 5 commands
Beginner
You've loaded your data. It's a new dataset. You have no idea what's in it. Here's the thing every experienced data scientist does before anything else — they look at it. Not all of it. Just enough to understand what they're dealing with.

These 5 commands are your flashlight in the dark. Run them in this order on every new dataset you touch. 
df.head()        # See the first 5 rows — "what does this look like?"
df.shape         # (rows, columns) — "how big is this?"
df.info()         # Column names, data types, non-null counts — "what's in here?"
df.describe()    # Stats for every numeric column — "any weird outliers?"
df.isnull().sum() # Count missing values per column — "what's broken?"
head() — Shows you the raw rows. You'll immediately spot formatting issues, unexpected characters, or columns that look wrong.

shape — Is this 100 rows or 1 million? Matters for what you do next.

info() — The most useful one. Tells you if a "number" column is stored as text (common bug!), which columns have missing data, and how much memory you're using.

describe() — If the minimum of "Age" is -5, something is wrong. If the max of "Price" is 9,999,999, someone fat-fingered a value. This catches all of that.

isnull().sum() — Missing data is the most common real-world problem. Know exactly where the holes are before you do anything else.
4
Selecting data — asking questions of your table
Beginner
Now you can see your data. But you don't always want all of it. Sometimes you want just one column. Sometimes just certain rows. This is the most important skill in Pandas — knowing how to ask for exactly what you need.

Pandas gives you two tools for this: .loc (select by label) and .iloc (select by position). People get confused by these. Here's the simplest way to think about it.
Analogy — loc vs iloc

Imagine a library. Every book has both a title and a shelf number.

.loc = "give me the book called 'Harry Potter'" — you use the name/label
.iloc = "give me the 3rd book on the 2nd shelf" — you use the position number

For most tables, they do similar things. The difference matters when your index has custom labels (like dates or names).

# Select one column → returns a Series
df['Name']

# Select multiple columns → returns a DataFrame
df[['Name', 'Score']]

# .loc — use labels (row label, column name)
df.loc[0]                  # The row where index == 0
df.loc[0:2]               # Rows 0, 1, 2 — NOTE: END IS INCLUSIVE with loc
df.loc[0, 'Name']          # Row 0, column 'Name'
df.loc[df['City']=='London', 'Score']  # Scores for London rows

# .iloc — use positions (like list indexing)
df.iloc[0]                 # First row (position 0)
df.iloc[0:3]              # Rows at positions 0, 1, 2 — END IS EXCLUSIVE
df.iloc[0, 1]             # Row 0, Column 1 (by number)
df.iloc[-1]               # Last row
⚠️ The most common beginner mistake: loc slicing is inclusive (loc[0:3] gives rows 0,1,2,3) but iloc slicing is exclusive (iloc[0:3] gives rows 0,1,2). This catches everyone at least once.
5
Filtering — "show me only the rows where..."
Beginner
This is where Pandas starts feeling like a superpower. Instead of scrolling through 80,000 rows looking for London sales over £500, you write one line and get exactly that. Instantly.

The way it works: you write a condition that produces a True/False for every row, then hand that mask to the DataFrame. It gives back only the True rows. 
# Single condition
df[df['Score'] > 80]

# Two conditions — wrap EACH in parentheses, use & not 'and'
df[(df['Score'] > 80) & (df['City'] == 'London')]

# OR condition
df[(df['City'] == 'London') | (df['City'] == 'Paris')]

# Better way to write OR: use .isin()
df[df['City'].isin(['London', 'Paris'])]

# Rows containing a string (partial match)
df[df['Name'].str.contains('Ali', case=False)]

# The .query() method — more readable for complex filters
df.query("Score > 80 and City == 'London'")
❌ Don't use Python's and / or keywords inside DataFrame filters. They don't work on arrays. Use & and | instead — and always wrap conditions in ().
6
Adding, changing, and removing columns
Beginner
Raw data is rarely in the exact shape you need. Maybe you need to create a new column from two existing ones, rename something, or delete columns you don't care about. This is part of every real data project — shaping the data to answer your specific question. 
# Add a new column derived from existing ones
df['Score_Boosted'] = df['Score'] * 1.1

# Add a column from a condition
df['Passed'] = df['Score'] >= 75   # True/False column

# Rename columns
df.rename(columns={'Score': 'Test_Score', 'City': 'Location'}, inplace=True)

# Drop a column you don't need
df.drop(columns=['Score_Boosted'], inplace=True)

# Sort by a column
df.sort_values('Test_Score', ascending=False)

# Reset the index after filtering/sorting
df.reset_index(drop=True, inplace=True)
✅ inplace=True modifies the DataFrame in-place so you don't need to reassign. Without it: df = df.drop(...). Both work — just be consistent.
Chapter 2 · Intermediate

Week 2. The data is messier than you expected.

You've explored the dataset. And you've noticed things. Some rows have blank values. Some dates are formatted wrong. Your manager wants a breakdown of sales by city. Someone wants the data merged with another file from a different department.

This is the real work. The basics got you through the door. These skills are what actually move the needle on a project.

1
Handling missing data — the most common real-world problem
Intermediate
In a perfect world, every cell in your dataset has a value. In the real world, surveys get skipped, sensors fail, forms go half-filled, and exports go wrong. Missing data — represented in Pandas as NaN (Not a Number) — is everywhere.

The wrong move is to panic and just delete every row with a missing value. Depending on the context, that could throw away 40% of your data. The right move is to understand why it's missing and choose a strategy accordingly. 
# Step 1: Find where the holes are
df.isnull().sum()               # Count NaN per column
df.isnull().mean() * 100        # % missing per column
df.notna()                          # True where NOT null (opposite of isnull)
df['Discount'].notna()               # Create boolean flag: True = discount applied

# Step 2: Decide your strategy

# Option A: Drop rows (use when < 5% missing and it's random)
df.dropna()
df.dropna(subset=['Age', 'Score'])   # Only drop if THESE columns are null

# Option B: Fill with a fixed value
df['Score'].fillna(0)               # Only do this if 0 is meaningful
df['City'].fillna('Unknown')

# Option C: Fill with stats (the smart way)
df['Age'].fillna(df['Age'].mean())      # Fill with average
df['Age'].fillna(df['Age'].median())    # Median is better if there are outliers

# Option D: Forward fill (for time series — carry last known value forward)
df.ffill()
df.bfill()  # Backward fill
Think about why the data is missing:

Missing randomly? (e.g., someone just didn't fill the form) → fill with mean or median, or drop if it's rare.
Missing because it doesn't apply? (e.g., "spouse name" for unmarried people) → fill with a specific value like "N/A".
Missing in a time series? (e.g., sensor went offline for 3 hours) → ffill() or bfill() carries the last known value forward/backward, which is usually the most realistic assumption.

Never blindly use fillna(0) — if the column is "Revenue", a 0 means "no revenue", not "no data". Those are very different things.
2
GroupBy — answering "what about each group?"
Intermediate
Your manager asks: "What's the average score per city?" Or: "Which product sold the most in each region?"

This is GroupBy territory. The concept is beautifully simple: split your data into groups, apply a calculation to each group, then combine the results back together. Three steps. Every time.
Analogy

Imagine sorting a pile of exam papers by class (split), calculating the average score for each class (apply), then writing each class's average on a board (combine). That's exactly what groupby does — but on any dataset, in one line.

# Basic: average score per city
df.groupby('City')['Score'].mean()

# Multiple aggregations at once
df.groupby('City').agg(
    avg_score  = ('Score', 'mean'),
    max_score  = ('Score', 'max'),
    num_people = ('Name',  'count')
)

# Group by multiple columns
df.groupby(['City', 'Passed'])['Score'].mean()

# transform — add the group stat back to original rows
# Example: add each person's city average as a new column
df['City_Avg'] = df.groupby('City')['Score'].transform('mean')

# Now you can compare each person to their city's average
df['Above_City_Avg'] = df['Score'] > df['City_Avg']
💡 agg() vs transform() — agg() shrinks your data (one row per group). transform() keeps your data the same size but fills in group-level stats next to each row. Use transform() when you want to compare individuals to their group.
3
Merging datasets — combining two tables into one
Intermediate
You have one file with customer names and IDs. Another file with those IDs and their purchase history. You need both together. This is merging — the Pandas equivalent of SQL's JOIN. It's one of the most important operations in data work.
Analogy — types of joins

Imagine two lists: a guest list (df1) and a meal preference list (df2). Not everyone on the guest list chose a meal, and some meal choices don't match a guest.

Inner join — only guests who also chose a meal (only matching rows)
Left join — all guests, with meal info where it exists (NaN if no match)
Outer join — everything from both lists, matched where possible

customers = pd.DataFrame({'ID': [1,2,3], 'Name': ['Alice','Bob','Charlie']})
orders    = pd.DataFrame({'ID': [2,3,4], 'Amount': [120,85,200]})

# Inner join — only IDs that appear in BOTH tables
pd.merge(customers, orders, on='ID', how='inner')
# ID=2 (Bob), ID=3 (Charlie) only — Alice has no order, ID=4 has no customer

# Left join — keep ALL customers, add order info where available
pd.merge(customers, orders, on='ID', how='left')
# All 3 customers. Alice gets NaN for Amount.

# Outer join — everything from both tables
pd.merge(customers, orders, on='ID', how='outer')

# When column names differ between tables
pd.merge(customers, orders, left_on='CustomerID', right_on='CustID')

# Stack rows (same columns, more rows)
pd.concat([df_jan, df_feb, df_mar], axis=0).reset_index(drop=True)
✅ After a left join, check merged_df.isnull().sum() — any NaN in the right table's columns means some IDs didn't match. This is often a data quality issue worth investigating.
4
Apply & Map — transforming data your way
Intermediate
Sometimes a column needs to be transformed in a way Pandas doesn't have a built-in function for. Maybe you need to convert scores to letter grades, clean up inconsistent text formatting, or combine two columns into one. apply() and map() let you run any custom logic on your data. 
# apply on a single column — run a function on every value
def to_grade(score):
    if score >= 90: return 'A'
    elif score >= 75: return 'B'
    elif score >= 60: return 'C'
    else: return 'F'

df['Grade'] = df['Score'].apply(to_grade)

# apply on a whole row (axis=1) — access multiple columns
df['Summary'] = df.apply(
    lambda row: f"{row['Name']} scored {row['Score']} in {row['City']}",
    axis=1
)

# map — swap values using a dictionary (fast & clean)
df['Grade_Points'] = df['Grade'].map({'A': 4.0, 'B': 3.0, 'C': 2.0, 'F': 0.0})
⚠️ apply() is convenient but slow on large datasets — it runs Python code row by row. In Chapter 3, you'll learn vectorized alternatives that do the same thing 100x faster.
5
String operations — cleaning messy text
Intermediate
Real data is full of messy strings. " london ", "LONDON", "London" — these all look different to Python, but they mean the same thing. The .str accessor gives you an entire toolkit for cleaning text, all vectorized (fast). 
# Fix common issues instantly
df['City'] = df['City'].str.strip().str.title()   # Remove spaces, fix casing

df['Name'].str.upper()           # ALL CAPS
df['Name'].str.lower()           # all lowercase
df['Name'].str.len()             # Character count
df['Name'].str.replace('Dr. ', '', regex=False)  # Remove prefix

# Split a column into two (e.g., "First Last" → two columns)
df[['First', 'Last']] = df['Full_Name'].str.split(' ', expand=True)

# Extract numbers or patterns using regex
df['Postcode'].str.extract(r'([A-Z]{1,2}\d{1,2})')

# Filter rows containing a substring
df[df['Email'].str.contains('@gmail.com', na=False)]
6
DateTime — making sense of dates
Intermediate
"How many sales happened in Q3?" "What's the weekly trend?" "How many days between sign-up and first purchase?" These are questions about time, and they require your date columns to actually behave like dates — not strings.

One common mistake: loading a CSV where "Date" is just stored as text. Pandas can't do date arithmetic on text. You need to convert it first. 
# Convert a text column to proper datetime
df['Date'] = pd.to_datetime(df['Date'])

# Or parse on load
df = pd.read_csv('data.csv', parse_dates=['Date'])

# Extract parts of the date
df['Year']    = df['Date'].dt.year
df['Month']   = df['Date'].dt.month
df['Weekday'] = df['Date'].dt.day_name()   # 'Monday', 'Tuesday'...
df['Quarter'] = df['Date'].dt.quarter

# Date arithmetic — days since date
df['Days_Ago'] = (pd.Timestamp('today') - df['Date']).dt.days

# Filter by date range
df[df['Date'] >= '2024-01-01']
df[df['Date'].between('2024-01-01', '2024-06-30')]

# Resample time series — group by time period
df.set_index('Date').resample('ME')['Revenue'].sum()  # Monthly total

Month 3. Your script works. But it takes 20 minutes.

Your code is correct. Your analysis is right. But the dataset grew — it's now 10 million rows. Your apply() loop takes 18 minutes. Your colleague's script crashes with a MemoryError. Your manager wants results daily.

This chapter is about the difference between code that works and code that works well. Speed. Memory. Readability. These are the skills that move you from analyst to engineer.

1
Vectorization — why your apply() is killing performance
Advanced
Here's something most people don't know when they start: apply() is basically a Python for-loop in disguise. It goes through every row one at a time in Python, which is slow. Vectorized operations, on the other hand, hand the entire computation to NumPy's C-compiled engine, which processes all rows at once.

On 1 million rows, this difference can be 100x. Not 10%. One hundred times faster.
❌ SLOW — Python loop disguised as apply
df['Boosted'] = df['Score'].apply(
    lambda x: x * 1.1
)

df['Grade'] = df['Score'].apply(
    lambda x: 'Pass' if x >= 50
    else 'Fail'
)
✅ FAST — Vectorized operations
df['Boosted'] = df['Score'] * 1.1

import numpy as np
df['Grade'] = np.where(
    df['Score'] >= 50,
    'Pass', 'Fail'
)
import numpy as np

# np.where — vectorized if/else
df['Label'] = np.where(df['Score'] > 80, 'High', 'Low')

# np.select — vectorized if/elif/else (multiple conditions)
conditions = [
    df['Score'] >= 90,
    df['Score'] >= 75,
    df['Score'] >= 60,
]
choices = ['A', 'B', 'C']
df['Grade'] = np.select(conditions, choices, default='F')

# Math operations are automatically vectorized
df['Z_Score'] = (df['Score'] - df['Score'].mean()) / df['Score'].std()
✅ Rule of thumb: if you can express your transformation as arithmetic, comparison, or a NumPy function — do that. Only reach for apply() when the logic genuinely can't be expressed any other way.
2
Memory optimization — fit 10x more data in the same RAM
Advanced
By default, Pandas makes conservative assumptions about your data. It stores integers as 64-bit (8 bytes each) even if your values only go up to 100. It stores text columns as Python objects — meaning every string is stored separately in memory, even if the same city name appears 500,000 times.

A few targeted changes to your data types can cut memory usage by 50–90%. On a 2GB dataset, that's the difference between crashing and running fine. 
# First: measure your current memory usage
df.memory_usage(deep=True).sum() / 1024**2  # in MB

# Downcast integers — use the smallest type that fits your values
df['Age']   = pd.to_numeric(df['Age'],   downcast='integer')
df['Score'] = pd.to_numeric(df['Score'], downcast='float')
# int64 (8 bytes) → int8 (1 byte) if values fit in [-128, 127]
# float64 (8 bytes) → float32 (4 bytes) for most practical uses

# The biggest win: category dtype for low-cardinality string columns
# If 'City' has 1 million rows but only 50 unique values...
df['City']  = df['City'].astype('category')  # ~90% less memory
df['Grade'] = df['Grade'].astype('category')

# Load only the columns you actually need
df = pd.read_csv('massive_file.csv', usecols=['Name', 'Score', 'City'])

# Process huge files in chunks instead of loading everything
results = []
for chunk in pd.read_csv('huge.csv', chunksize=50_000):
    filtered = chunk[chunk['Score'] > 80]
    results.append(filtered)
df = pd.concat(results, ignore_index=True)
When a column has type object (Python strings), Pandas stores a separate string object in memory for each row. If "London" appears 500,000 times, it stores "London" 500,000 times — 6 characters × 500,000 = 3MB just for one value.

With category, Pandas builds a lookup table: {0: "London", 1: "Paris", 2: "Tokyo"}. Then each row just stores a small integer (0, 1, or 2). Instead of 3MB, it's 500,000 × 1 byte = 500KB. A 6x reduction — and that's just for one value. With many unique strings, the savings are even bigger.
3
Method chaining — writing code that reads like a story
Advanced
Here's a dirty secret: most real data pipelines are just a sequence of transformations. Load, clean, filter, reshape, aggregate. When you write each step as a separate assignment (df = df.drop(...), df = df.rename(...)), it works — but it's hard to read and easy to make mistakes.

Method chaining lets you write the entire pipeline as a single, flowing expression. Each step feeds into the next. It reads top-to-bottom like a recipe.
❌ Before — scattered assignments
df = df.dropna()
df = df.rename(
  columns={'old':'new'})
df = df[df['Age'] > 18]
df = df.sort_values('Score')
df = df.reset_index(drop=True)
✅ After — clean pipeline
df = (
  df
  .dropna()
  .rename(columns={'old':'new'})
  .query("Age > 18")
  .sort_values('Score')
  .reset_index(drop=True)
)
# .pipe() — slot your own function into the chain
def add_rank(df, col):
    df[col + '_rank'] = df[col].rank(pct=True)
    return df

def log_shape(df):
    print(f"Shape: {df.shape}")   # Great for debugging pipelines
    return df

result = (
    df
    .dropna(subset=['Score', 'City'])
    .query("Score >= 50")
    .pipe(log_shape)              # Check rows at this point
    .pipe(add_rank, 'Score')      # Add a custom column
    .groupby('City').agg(avg=('Score', 'mean'))
    .sort_values('avg', ascending=False)
    .reset_index()
)
4
Window functions — trends, rolling averages, and lag
Advanced
Sometimes a single row's value only makes sense in context. "Sales this week were £40,000" — is that good or bad? You need to compare it to recent weeks. Window functions let you look at a "window" of rows around each row — without losing any data. 
# 7-day rolling average (smooths out day-to-day noise)
df['Sales_MA7'] = df['Sales'].rolling(window=7).mean()

# Rolling standard deviation (measures volatility)
df['Volatility'] = df['Sales'].rolling(7).std()

# Cumulative sum and max (running totals)
df['Running_Total'] = df['Sales'].cumsum()
df['All_Time_High'] = df['Sales'].expanding().max()

# Lag & lead — compare to previous/next row
df['Yesterday']    = df['Sales'].shift(1)   # Previous row's value
df['Daily_Change'] = df['Sales'] - df['Sales'].shift(1)
df['Pct_Change']   = df['Sales'].pct_change() * 100

# Rank within groups (e.g., top performer per city)
df['City_Rank'] = df.groupby('City')['Score'].rank(
    method='dense', ascending=False
)
top_per_city = df[df['City_Rank'] == 1]
5
eval() and query() — fast string-based computation
Advanced
For very large DataFrames, even standard vectorized operations can be slow because they create large temporary arrays in memory. eval() and query() bypass this — they use the numexpr library under the hood, processing the expression without ever creating those intermediary arrays. Faster. Less memory. 
# eval — compute expressions without intermediate arrays
df.eval('Total = Score + Bonus', inplace=True)

# Multiple computations in one eval call
df.eval("""
    Total      = Score + Bonus
    Normalised = Score / Score.max()
    Pass       = Score >= 50
""", inplace=True)

# query — filter without creating boolean mask arrays
df.query("Score > 80 and City == 'London'")

# Use Python variables inside query/eval with @ prefix
threshold = 80
city = 'London'
df.query("Score > @threshold and City == @city")

# Also works in eval
df.eval("Adjusted = Score - @threshold")
💡 eval() and query() shine most on DataFrames with millions of rows. For small DataFrames (<10k rows), the overhead isn't worth it — just use regular operations.
